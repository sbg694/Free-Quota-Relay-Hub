# 00 · 背景、黑话与三种池化模式

## 1. 「中转站」到底是什么

**API 中转站**（也叫「API 代理」「镜像站」「逆向站」）是一个把上游模型能力重新包装成统一接口再卖/再送的服务。技术上通常就是：

```
你的客户端 ──(OpenAI 兼容协议)──▶ 中转站网关 ──(各家原生/兼容协议)──▶ OpenAI / Anthropic / Google / 国内大模型
```

它存在的原因是三条：

1. **支付**：海外厂商要外币卡，中转站收人民币。
2. **网络**：部分厂商接口在境内不可直连。
3. **协议统一**：把 Claude、Gemini、通义、DeepSeek 都包成 `/v1/chat/completions`，客户端只需改 `base_url`。

代价是：定价不透明（倍率）、可用性不保证（上游随时挂/跑路）、数据要过第三方（日志留存风险）。

本项目**不评判**中转站本身，只研究「如何把手里的额度资源管理好」。

## 2. 黑话表（看中转站公告/群聊必备）

| 黑话 | 含义 | 为什么要关心 |
| --- | --- | --- |
| 渠道 / channel | 上游线路，一个中转站内部可能有多条渠道（官方直连、逆向、某云代理） | 同一模型不同渠道的质量、封号率差别很大 |
| 倍率 | 计费系数，`消耗 = 官方价 × 倍率` | 免费额度按「额度」计，倍率决定实际能用多少 |
| 额度 / 余额 | 账户里的可用金额或 token 数，常见「$」「¥」「points」混用 | 台账要统一换算口径 |
| 签到 / 白嫖额度 | 每日签到、邀请、活动送的额度 | 本项目主要的「零散额度」来源之一 |
| 逆向 / 反代 | 用网页版 Cookie 或逆向协议模拟 API | 极不稳定，封号率高，不适合做奠基来源 |
| 池 / 号池 | 多个 key 或账号组成的一个可轮询集合 | 本项目核心数据结构 |
| 探活 | 定期发最小请求验证 key 是否可用 | 决定「是否拉黑/恢复」 |
| 失败转移 / failover | 一个来源失败后自动换下一个 | 决定整体稳定性 |
| RPM / TPM / RPD | 每分钟请求数 / 每分钟 token / 每天请求数 | 池化调度的硬约束 |
| 冷却 | 命中 429 后该 key 在一段时间内不再被选中 | 避免无谓重试放大封禁风险 |

## 3. 三种「池化」模式，别混为一谈

| 模式 | 池子里放什么 | 典型实现 | 合规性 | 稳定性 |
| --- | --- | --- | --- | --- |
| **A. 自管上游 key 池** | 自己在各家**官方**注册得到的 API key（含官方免费层） | 自建网关 + key 轮询（如 one-api / new-api / LiteLLM + 自定义路由） | 🟢 较高，遵守单账号限额即可；但「多账号轮换规避限额」在多数 ToS 里被禁止 | 中高（官方限流明确） |
| **B. 聚合多个中转站的 key** | 在多个第三方中转站各买/各领一个 key | 统一网关做多上游路由（本项目 MVP 主要场景） | 🟡 取决于中转站条款；上游可能有「禁止转售/共享」 | 中（上游跑路是系统性风险） |
| **C. 抓网页 / 逆向** | 网页 Cookie、逆向协议 | 逆向工具 | 🔴 高风险，明确违反 ToS，可能涉及法律 | 低 |

> **本项目的设计默认落在 A + B**：把「官方免费层」和「中转站免费/低价额度」都视为**上游 provider**，用同一套抽象管理。C 只作为「已知但排除」的选项记录在 [04-合规](04-risks-and-compliance.md)。

## 4. 一个请求穿过系统时发生什么

```
client ─▶ Gateway(鉴权, 模型名映射) ─▶ Router(选池 → 选 key) ─▶ Upstream
                                         │                        │
                                         ├─ 健康分/权重/额度检查   ├─ 429 → 冷却 key, 换候选
                                         └─ 并发槽占用             ├─ 401/403 → 拉黑, 换候选
                                                                  └─ 200 → 记流水、回填用量
```

关键设计点（详见 [03-architecture](03-architecture.md)）：

1. **模型名归一**：客户端要 `gpt-4o`，实际可能由 `openrouter/openai/gpt-4o` 或某中转站的 `gpt-4o` 承接 → 需要模型别名表。
2. **选路是二维的**：先选「能服务这个模型的池」，再在池内选 key（权重 × 健康分 × 剩余额度 × 并发余量）。
3. **失败分类处理**：不是所有错误都该重试；流式请求已经吐字后不能再换上游。
4. **记账要幂等**：上游返回的 usage 有时缺失，需要本地估算兜底（tiktoken / 字符数近似），并标记 `estimated=true`。

## 5. 我们真正想优化的指标

| 指标 | 目标（MVP） | 说明 |
| --- | --- | --- |
| 可用性 | 单上游故障时整体成功率 > 99% | 靠 pool + failover |
| 首字延迟 P95 | ≤ 上游直连 + 200ms | 网关不能成为瓶颈 |
| 额度利用率 | 免费额度过期前用掉 > 80% | 靠账本 + 到期提醒 |
| 人工干预次数 | 每周 ≤ 1 次 | 靠探活与告警 |
| 密钥泄漏面 | 0（本地加密存储） | 靠安全设计 |

## 6. 术语速查（工程侧）

- **SSE 透传**：流式响应必须边收边转，不能先缓冲全量；同时要处理上游 `[DONE]` 与异常断流。
- **遥测字段**：`request_id / pool / key_id / model_alias / upstream_model / status / first_token_ms / total_ms / prompt_tokens / completion_tokens / estimated`。
- **额度单位**：建议内部统一用「USD 等价额度」+「token 计数」双轨，避免各家计价单位不同导致账本失真。
